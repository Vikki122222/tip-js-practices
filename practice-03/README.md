## Эксперименты с DOM и событиями

### Эксперимент 1. Отсутствующий элемент и пустая коллекция

**Прогноз:**  
`querySelector` при отсутствии совпадения вернёт `null`.  
`querySelectorAll` вернёт пустой `NodeList`, длина которого равна `0`.

**Фактический результат:**  
В Console получено:
- отсутствующий элемент: `null`;
- пустая коллекция: `0`.

**Вывод:**  
`querySelector` возвращает `null`, если элемент не найден.  
`querySelectorAll` возвращает пустую коллекцию, у которой можно проверить свойство `length`.

### Эксперимент 2. Значение из dataset

**Прогноз:**  
Значение `data-task-id` будет прочитано из `dataset` как строка.  
После преобразования через `Number` получится числовой идентификатор.

**Фактический результат:**  
В Console получено:
- `dataset.taskId: 23`, тип `string`;
- числовой id: `23`.

**Вывод:**  
Значения `data-*` читаются из `dataset` как строки.  
Перед передачей идентификатора в функции работы с задачами его необходимо преобразовать в число.

### Эксперимент 3. Статический NodeList

**Прогноз:**  
Сохранённый результат `querySelectorAll` не изменится после добавления новых элементов.  
Новый вызов `querySelectorAll` должен увидеть актуальное количество записей.

**Фактический результат:**  
Изначально длина сохранённого `NodeList` была равна `1`.  
После добавления новых записей старый `NodeList` продолжал иметь длину `1`, а новый `querySelectorAll` возвращал коллекцию с увеличивающимся количеством элементов: `2`, `3`, затем `4`.

**Вывод:**  
`querySelectorAll` возвращает статический `NodeList`.  
Он не обновляется автоматически после изменений DOM, поэтому для получения актуального набора элементов необходимо выполнить новый запрос.

### Эксперимент 4. Вывод текста без HTML-интерпретации

**Прогноз:**  
Если строку с HTML-тегами присвоить через `textContent`, браузер выведет её как обычный текст и не создаст элемент `strong`.

**Фактический результат:**  
После нажатия на кнопку «Изменить заголовок» на странице отобразилась строка:

`<strong>Это текст, а не HTML</strong>`

Тег `strong` не был создан и текст не стал жирным.

**Вывод:**  
`textContent` выводит строку как текст и не интерпретирует её как HTML-разметку. Поэтому этот способ подходит для вывода названий задач.

### Эксперимент 5. Распространение события

**Прогноз:**  
При нажатии на вложенный `span` событие сначала пройдёт фазу захвата, затем обработчик родительской кнопки и контейнера получат это же событие при всплытии.  
`event.target` будет указывать на элемент, по которому нажали, а `event.currentTarget` — на элемент, чей обработчик выполняется в данный момент.

**Фактический результат:**  
В журнале получена последовательность:

1. `phase=1`, `target=lab-label`, `currentTarget=lab-card`;
2. `phase=3`, `target=lab-label`, `currentTarget=lab-button`;
3. `phase=3`, `target=lab-label`, `currentTarget=lab-card`.

**Вывод:**  
`event.target` остаётся исходной целью события, а `event.currentTarget` зависит от текущего обработчика. Благодаря всплытию событие от вложенного `span` можно обработать на родительской кнопке или контейнере.

## Создание карточек и отображение списка

В файле `src/task-view.js` реализованы функции `createTaskElement` и `renderTaskList`.

Карточка задачи создаётся средствами DOM без использования `innerHTML`. Название задачи выводится через `textContent`.

Для карточки реализованы:
- идентификатор задачи через `data-task-id`;
- название задачи;
- статус `Выполнена` или `В работе`;
- отображение приоритета;
- кнопка изменения статуса;
- кнопка удаления;
- состояние `aria-pressed`.

Функция `renderTaskList` заменяет дочерние элементы списка через `replaceChildren`, поэтому повторная отрисовка не приводит к накоплению одинаковых карточек.

**Фактический результат проверки:**  
Проверки карточки и отображения списка пройдены успешно.

## Фильтрация задач

В файле `src/task-selectors.js` реализована функция `getVisibleTasks`.

Поддерживаются три режима:
- `all` — все задачи;
- `pending` — только невыполненные задачи;
- `completed` — только выполненные задачи.

Фильтрация не изменяет исходный массив задач. Для режима `all` также возвращается новый массив.

**Фактический результат проверки:**  
Все пять автоматических проверок функции `getVisibleTasks` пройдены успешно.

## Делегирование событий и действия с задачами

В `src/main.js` реализован обработчик `handleTaskListClick`.

Для обработки действий используется делегирование событий: один обработчик установлен на контейнер списка задач. Нажатая кнопка определяется через `closest("button[data-action]")`, поэтому обработка работает в том числе при нажатии на вложенный `span`.

Идентификатор задачи читается из `data-task-id`, преобразуется в число через `Number` и проверяется с помощью `Number.isSafeInteger`.

Для изменения состояния используются функции из ПР2:
- `findTaskById`;
- `setTaskCompleted`;
- `removeTask`.

При успешной операции сохраняется новый массив задач, после чего вызывается повторная отрисовка интерфейса. При ошибке исходные данные не изменяются, а пользователю выводится сообщение.

## Сводка и пустые состояния

В `src/task-view.js` реализованы функции `renderSummary` и `renderEmptyState`.

Функция `renderSummary` получает общую статистику через `getTaskStats` и обновляет:
- общее количество задач;
- количество выполненных;
- количество невыполненных;
- прогресс;
- количество показанных задач.

Общая статистика рассчитывается по полному массиву задач, а показатель «Показано» — по текущей видимой выборке.

Функция `renderEmptyState` различает два состояния:
- полностью пустой список;
- отсутствие задач по выбранному фильтру.

При наличии видимых задач сообщение очищается и скрывается.

## Отрисовка приложения

В `src/main.js` реализована функция `renderApp`.

Функция:
- получает видимый список задач через `getVisibleTasks`;
- обновляет карточки через `renderTaskList`;
- обновляет общую статистику через `renderSummary`;
- обновляет пустое состояние через `renderEmptyState`;
- синхронизирует активную кнопку фильтра с текущим значением `currentFilter`.

Полный массив `currentTasks` при этом не изменяется.

## Обработка фильтров

В `src/main.js` реализован обработчик `handleFilterClick`.

Кнопка фильтра определяется через `closest("button[data-filter]")`, поэтому обработка работает и при нажатии на вложенные элементы кнопки.

Поддерживаются значения:
- `all`;
- `pending`;
- `completed`.

При выборе фильтра изменяется только `currentFilter`. Полный массив `currentTasks` не изменяется. После изменения фильтра вызывается `renderApp`, который заново рассчитывает видимый список и обновляет интерфейс.
