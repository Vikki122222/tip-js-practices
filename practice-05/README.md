## 6.2. Эксперимент с очередями выполнения

Прогнозы записаны до запусков: [event-loop-predictions.txt](reports/event-loop-predictions.txt).

| Эксперимент | Прогноз до запуска | Фактический порядок | Итог |
|---|---|---|---|
| Исходный `event-loop.js` | A B C D E F | A B C D E F | Совпало |
| Собственная микрозадача G после синхронной части | A B C D E G F | A B C D E G F | Совпало |
| Дополнительный опыт: удалён обработчик D | A B C E F | A B C E F | Совпало |

- A выполняется синхронно при старте скрипта.
- D регистрируется как обработчик Promise.
- Вызов async-функции сразу выводит B; её продолжение E после `await null` ставится в очередь микрозадач после D.
- C завершает синхронный участок.
- После освобождения стека выполняются D и E, а в дополнительном примере — затем G.
- F является задачей таймера. Задержка 0 не означает немедленное выполнение внутри текущего стека.
- Если удалить D, продолжение E остаётся микрозадачей и всё равно выполняется до F.

## 6.4–6.5. Реализация общего клиента

| Требование | Реализация | Подтверждение |
|---|---|---|
| Абсолютный `baseUrl` | Допустимы HTTP(S), запрещены query и hash; удаляется завершающий `/`. | Штатные № 01, 04; собственная № 10. |
| Относительный путь | Соединяется с базовым путём без двойного разделителя; абсолютный URL не принимается. | Штатная № 01; собственная № 10. |
| Query | Новый объект `URL`, параметры добавляются через `searchParams.set`. `undefined`, `null`, `""` пропускаются, `false` и `0` сохраняются. Входной объект не меняется. | Штатные № 02–03; собственные № 01–02. |
| Конфигурация | Проверяются `fetchFn`, тайм-аут, объект параметров и внешний `AbortSignal`. | Штатная № 04; собственная № 10. |
| GET и Accept | Передаются `method: "GET"`, `Accept: application/json`, объединённый сигнал. | Штатная № 05. |
| HTTP | Статус проверяется отдельно от отказа `fetch`. Для ошибки сохраняются статус и поля `payload.error`. | Штатные № 08–09, 16; интеграционные № 07–09. |
| Нет тела | Успешный 204 возвращает `null`. | Штатная № 07. |
| Content-Type | До разбора успешного тела проверяется тип `application/json` с учётом регистра и параметров после `;`. | Штатная № 10; интеграционная № 11. |
| JSON | `response.json()` ожидается один раз; `SyntaxError` сохраняется в `cause`. | Штатные № 06, 11. |
| Тайм-аут | `AbortSignal.timeout()` передаётся непосредственно `fetch`, а не только в `Promise.race`. | Штатная № 14; интеграционная № 12; собственная № 05. |
| Внешняя отмена | Сигналы объединяются через `AbortSignal.any()`, определяется причина первого сработавшего сигнала. | Штатная № 15; интеграционная № 13; собственные № 04, 06. |

Ошибки конфигурации и неверные входные аргументы являются `TypeError`. `ApiError` представляет ошибки выполнения HTTP-операции и проверки ответа.

HTTP-ошибка остаётся `http`, даже если её тело не является JSON или содержит повреждённый JSON. Ошибки обработки ответа не перехватываются широким `catch`, который мог бы превратить их в `network`.

## Классификация ошибок

Все строки ниже проверены фактически; значения остальных полей и исходные сообщения сохранены в `reports/experiments.json`.

| Сценарий | Ожидаемый kind | Фактические поля ApiError | Итог |
|---|---|---|---|
| Задача 999 | `http` | `{"kind":"http","status":404,"code":"TASK_NOT_FOUND","details":{"id":999}}`; URL: `http://127.0.0.1:46015/api/tasks/999` | Пройдено |
| `completed=yes` | `http` | `{"kind":"http","status":400,"code":"INVALID_QUERY","details":null}`; URL: `http://127.0.0.1:46015/api/tasks?completed=yes` | Пройдено |
| `/debug/error` | `http` | `{"kind":"http","status":503,"code":"SERVICE_UNAVAILABLE","details":null}`; URL: `http://127.0.0.1:46015/api/debug/error` | Пройдено |
| `/debug/invalid-json` | `invalid-response` | `{"kind":"invalid-response","status":null,"code":null,"details":null}`; cause: `SyntaxError`; URL: `http://127.0.0.1:46015/api/debug/invalid-json` | Пройдено |
| `/debug/text` | `invalid-response` | `{"kind":"invalid-response","status":null,"code":null,"details":null}`; URL: `http://127.0.0.1:46015/api/debug/text` | Пройдено |
| API остановлен | `network` | `{"kind":"network","status":null,"code":null,"details":null}`; cause: `TypeError`; URL: `http://127.0.0.1:46015/api/health` | Пройдено |
| 150 мс при тайм-ауте 20 мс | `timeout` | `{"kind":"timeout","status":null,"code":null,"details":null}`; cause: `TimeoutError`; URL: `http://127.0.0.1:46015/api/debug/delay?ms=150` | Пройдено |
| Явный `AbortController.abort()` | `aborted` | `{"kind":"aborted","status":null,"code":null,"details":null}`; cause: `AbortError`; URL: `http://127.0.0.1:46015/api/debug/delay?ms=150` | Пройдено |

`network` означает отсутствие полученного HTTP-ответа. `timeout` означает превышение заданного времени, `aborted` — внешнюю отмену. Неверный `Content-Type`, повреждённый JSON и нарушение схемы классифицируются как `invalid-response`.

## 6.6. Предметный API задач

Фильтры `completed`, `priority`, `categoryId`, `q` проверяются до запроса. `completed` остаётся boolean; `categoryId` должен быть положительным безопасным целым; `q` очищается через `trim()` и ограничивается длиной 100. Неизвестные фильтры и неверные типы отклоняются без HTTP-запроса. Отсутствующее значение `undefined` пропускается.

Задача проверяется по пяти обязательным полям: положительные безопасные `id` и `categoryId`, непустое название длиной до 100 после `trim`, логический `completed`, допустимый `priority`.

Для категории проверяются положительный безопасный `id` и непустое имя длиной до 100 после `trim`. В коллекциях запрещены повторяющиеся id. `meta.total` должен быть целым и равняться длине `data`. Для списка задач также требуется объект `meta.filters`. Ответ одной задачи должен соответствовать запрошенному id.

| Вызов | Фактический результат |
|---|---|
| `getTasks()` | 12 задач, ID `[1,4,7,10,13,16,19,22,25,28,31,34]` |
| `getTasks({ completed: false, priority: "high" })` | ID `[4,13,34]`, total 3 |
| `getTaskById(25)` | `{"id":25,"title":"Исправить обработку ошибок","completed":true,"priority":"high","categoryId":2}` |
| `getCategories()` | `[{"id":1,"name":"Учёба"},{"id":2,"name":"Проект"},{"id":3,"name":"Организация"}]` |
| `loadInitialData(...)` | Объект `{ tasks, categories, meta }`, задачи и категории начинают загружаться до общего await. |

## 6.7. Последовательное и параллельное ожидание

Для сравнения выполнены два независимых GET-запроса `/debug/delay?ms=150`. Они моделируют задержку получения двух ресурсов. На каждый сценарий приходится три измерения. Искусственные задержки не включены в `task-api.js` или рабочий `main.js`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Среднее, мс |
|---|---:|---:|---:|---:|
| Два последовательных await | 308.1 | 304.9 | 302.7 | 305.2 |
| Promise.all | 152.9 | 152.1 | 153.3 | 152.7 |

При последовательном ожидании второй запрос начинается после завершения первого, поэтому задержки складываются. При `Promise.all` запросы уже запущены и ожидаются совместно, поэтому интервалы ожидания перекрываются. Это не означает параллельное выполнение JavaScript-кода.

Замеры зависят от компьютера, планировщика и сети. Наблюдаемое соотношение не является обещанием точного ускорения на любом компьютере. Отказ одного Promise отклоняет `Promise.all`, но автоматически не отменяет оставшийся запрос.

## 6.8. Тайм-аут и внешняя отмена

- Запрос `/debug/delay?ms=150` с `timeoutMs: 20` завершился `ApiError` с `kind: "timeout"`; в `cause` сохранён `TimeoutError`.
- Запрос с внешним сигналом и тайм-аутом 1000 мс после `controller.abort()` завершился `kind: "aborted"`; в `cause` сохранён `AbortError`.
- Собственная проверка заранее отменённого сигнала подтвердила, что `fetchFn` вообще не вызывается.
- Дополнительно проверены тайм-аут и внешняя отмена после получения Response, во время чтения тела. Они сохраняют виды `timeout` и `aborted`, а не превращаются в ошибку JSON.

## Вывод

Реализован переиспользуемый JSON-клиент для учебного HTTP API и предметный модуль задач. URL формируется стандартными средствами с сохранением false и безопасным кодированием query. Ответ проверяется по типу Response, статусу, Content-Type, синтаксису JSON и предметной схеме.

Ошибки разделены на http, network, invalid-response, timeout и aborted. Проверены 204, ошибочный статус без корректного JSON, отмена до начала запроса и прерывание при чтении тела. Независимые ресурсы загружаются через Promise.all.

Все штатные наборы прошли без ошибок: API — 18/18, клиент — 26/26, интеграция — 13/13. Дополнительно прошли 11 собственных проверок. Вариант № 3 получил `[4,13,16,25,34]`, meta.total равен 5. Фактические протоколы, замеры и трасса отладки включены в папку reports.

Ожидание Promise относится к моменту получения результата; HTTP-ошибка означает полученный ответ с неуспешным статусом; network — отсутствие ответа; invalid-response — непригодное тело или схема; timeout и aborted различают ограничение времени и внешнюю отмену.

Работа подготовлена к загрузке в существующий личный репозиторий. Публикация на GitHub на этапе подготовки файлов не выполнялась. После загрузки для сдачи используется ссылка на папку `practice-05` этого репозитория.
